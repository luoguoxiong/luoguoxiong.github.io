# RAG 检索增强生成：从原理到工程实践

> 大语言模型知识截止、参数记忆有限、无法访问私有数据。RAG（Retrieval-Augmented Generation）通过「先检索、后生成」的方式，把外部知识注入 LLM，是当前企业落地大模型最务实的方案。本文系统梳理 RAG 的完整流程与工程要点。

## 一、为什么需要 RAG

直接用 LLM 回答问题，会遇到三个硬伤：

1. **知识截止**：模型训练数据有截止日期，无法回答「最新」的信息
2. **幻觉**：模型不知道答案时，会一本正经地编造
3. **私有数据缺失**：企业的文档、数据库、内部知识，模型从未见过

微调（Fine-tuning）能解决一部分问题，但它：

- 成本高（需要标注数据 + GPU 训练）
- 更新慢（每次知识更新都要重新训练）
- 不可解释（不知道答案从哪来）

RAG 的思路很朴素：**既然模型记不住，那就让它「开卷考试」**。每次提问时，先从知识库检索相关内容，再把检索结果和问题一起喂给模型，让模型基于检索到的内容回答。

```
用户提问
   │
   ▼
[检索] 从知识库找相关文档片段
   │
   ▼
[增强] 把检索结果拼进 Prompt
   │
   ▼
[生成] LLM 基于上下文回答
```

### RAG vs 微调

| 维度 | RAG | 微调 |
|------|-----|------|
| 知识更新 | 增删文档即可，实时 | 需重新训练，慢 |
| 成本 | 低（只推理） | 高（训练 + 标注） |
| 可解释性 | 强（可溯源到文档） | 弱 |
| 适合场景 | 事实问答、知识检索 | 风格学习、领域适配 |
| 幻觉控制 | 好（有据可依） | 一般 |

两者不是非此即彼：**RAG 管知识，微调管能力**，实践中常组合使用。

## 二、RAG 完整流程

一个生产级 RAG 系统包含三个阶段：**索引、检索、生成**。

```
                         ┌──────────────────────────────────────┐
    离线阶段               │              索引阶段               │
                         │  文档 → 切分 → 向量化 → 存入向量库     │
                         └──────────────┬───────────────────────┘
                                        │
────────────────────────────────────────┼──────────────────────────
    在线阶段                              │
                         ┌──────────────▼───────────────────────┐
    用户提问 ──────────► │              检索阶段                 │
                         │  query 向量化 → 相似检索 → 重排序      │
                         └──────────────┬───────────────────────┘
                                        │
                         ┌──────────────▼───────────────────────┐
                         │              生成阶段                 │
                         │  构造 Prompt → LLM 生成 → 引用溯源    │
                         └──────────────────────────────────────┘
```

下面逐阶段拆解。

## 三、索引阶段：把文档变成可检索的结构

索引阶段决定了检索质量的上限。它包含四步：加载、切分、向量化、存储。

### 3.1 文档加载

知识库的原始形态多样：PDF、Markdown、HTML、数据库、API。加载时要提取**纯文本 + 元数据**。

```
PDF      -> 提取文字（注意表格、图片、多栏排版）
Markdown -> 去标记，保留标题层级
数据库   -> SQL 查询 + 字段映射
网页     -> 正文抽取（去除导航、广告）
```

**元数据**很重要：来源文件、页码、章节标题、时间戳。它们不仅用于溯源，还能做**过滤检索**（如只搜某个时间段、某个文档分类）。

### 3.2 文本切分（Chunking）

切分是 RAG 最影响效果的环节。切太大，检索精度低（一个 chunk 混入太多无关信息）；切太小，语义不完整（上下文断裂）。

**常见策略：**

| 策略 | 原理 | 适用场景 |
|------|------|---------|
| 固定长度 | 按 N 个 token 切，带 overlap | 通用、简单 |
| 递归切分 | 按分隔符层级切（段落 > 句子 > 词） | Markdown / 文档 |
| 语义切分 | 用 embedding 相邻度检测主题变化 | 长文档 |
| 结构化切分 | 按 HTML 标签 / Markdown 标题切 | 有结构的文档 |

**Overlap（重叠）** 是固定切分的关键设计：相邻 chunk 保留 10%~20% 的重叠内容，避免一句话被切两半导致语义断裂。

```
chunk1: [A B C D | E F]
chunk2:           [E F | G H I J]
                  ↑ overlap
```

**经验值：** chunk 大小一般取 300~800 token，overlap 取 chunk 的 10%~20%。文档越长越规整，chunk 可以偏大；问答场景 chunk 偏小。

### 3.3 向量化（Embedding）

把文本片段变成高维向量，使语义相近的文本在向量空间距离也近。这是语义检索的基础。

```
"如何重置密码"     -> [0.12, -0.35, 0.88, ...]  (768维)
"密码找回方法"     -> [0.11, -0.33, 0.85, ...]  (向量很近 ✓)
"今天的天气不错"   -> [-0.5, 0.72, 0.01, ...]   (向量很远 ✗)
```

**Embedding 模型选型要点：**

| 类型 | 代表 | 特点 |
|------|------|------|
| 通用英文 | text-embedding-3-small (OpenAI) | 效果好，但需 API、数据出境 |
| 多语言 | bge-m3、multilingual-e5 | 中英文兼顾，可本地部署 |
| 中文优化 | bge-large-zh、m3e-base | 中文检索效果好 |
| 轻量级 | bge-small、GTE-small | 速度快、资源省 |

选型核心：**语言匹配 + 维度适中 + 是否可私有部署**。企业内部数据要本地部署 embedding 模型，避免数据外泄。

### 3.4 向量存储

向量库负责存储 embedding 并支持**近似最近邻（ANN）**检索。精确最近邻是 O(N) 的，不可行，所以都用近似算法：

| 向量库 | 索引算法 | 特点 |
|--------|---------|------|
| FAISS | IVF / HNSW | Meta 开源，纯库，高性能 |
| Milvus | HNSW / IVF / DiskANN | 分布式、云原生、功能全 |
| Qdrant | HNSW | Rust 实现、轻量、带过滤 |
| Chroma | HNSW | 嵌入式、上手快、适合原型 |
| pgvector | HNSW / IVFFlat | PostgreSQL 扩展、跟业务库一体 |

**HNSW** 是当前最主流的 ANN 算法：基于分层小世界图，查询速度快、召回率高，但内存占用大。**IVF** 通过聚类分桶加速，内存省但召回略低。

除了向量，还要存**原始文本和元数据**，检索时一并返回用于生成。

## 四、检索阶段：找到最相关的内容

### 4.1 检索方式对比

| 方式 | 原理 | 优势 | 劣势 |
|------|------|------|------|
| 稀疏检索 (BM25) | 关键词精确匹配 | 零依赖、专有名词命中准 | 不理解语义 |
| 稠密检索 (向量) | embedding 语义相似 | 语义泛化（同义、近义） | 精确匹配弱、依赖模型 |
| 混合检索 | 两路并行 + 融合 | 兼顾精确与语义 | 实现复杂 |

**为什么需要混合检索？** 两个典型案例：

```
case 1: 用户搜 "React 18 的 useTransition"
  向量检索: 可能返回 "React Hooks 性能优化"（语义近但没命中）
  BM25: 精确命中 useTransition ✓

case 2: 用户搜 "怎么让组件不卡"
  BM25: "组件""卡" 命中一堆无关文档
  向量检索: 语义匹配 "性能优化""渲染卡顿" ✓
```

### 4.2 混合检索的融合策略

两路检索各取 top-N 后，需要把分数统一排序。常用方法：

**RRF（Reciprocal Rank Fusion）：**

```
score(d) = Σ  1 / (k + rank_i(d))
```

不看原始分数，只看排名。简单、无需归一化，是生产中最常用的融合策略。

**加权融合：**

```
score(d) = w_bm25 × norm_bm25(d) + w_dense × norm_dense(d)
```

需要对两路分数做 min-max 归一化，再按权重加权。权重通过调参确定，一般 0.3~0.7 之间。

### 4.3 查询改写（Query Rewriting）

用户的原始 query 往往口语化、模糊、缺上下文。直接用原 query 检索效果差，需要先改写：

```
原始: "那个性能的"
改写: "React 组件性能优化方案"

原始: "跟上次一样的报错"
改写: （结合历史对话）"TypeError: Cannot read property 'map' of undefined"
```

常见改写技术：

| 技术 | 原理 |
|------|------|
| Query Expansion | 用 LLM 生成多个同义 query，分别检索后合并 |
| HyDE | 让 LLM 先「假设一个答案」，用假答案的向量去检索 |
| Query Decomposition | 把复杂问题拆成子问题，分别检索 |
| Multi-Query | 生成多个不同角度的 query，扩大召回 |

**HyDE** 的直觉是：答案的 embedding 比问题的 embedding 更接近文档的 embedding（因为答案和文档用词更接近）。

### 4.4 重排序（Reranking）

向量检索是**双塔模型**（query 和 doc 独立编码），速度快但精度有限。重排序用**交叉编码器（Cross-Encoder）**：把 query 和 doc 拼在一起输入模型，输出精确的相关性分数。

```
向量检索 (粗排)                    重排序 (精排)
query embedding ─┐               ┌─ (query, doc1) → Cross-Encoder → 0.92
                  ├─ ANN top-50 ──┤─ (query, doc2) → Cross-Encoder → 0.71
doc embeddings  ──┘               └─ (query, doc50) → Cross-Encoder → 0.05
  (独立编码，快)                     (联合编码，准但慢)
```

Cross-Encoder 不能预计算（query 和 doc 要一起输入），所以只能对少量候选做精排。典型流程：**向量检索取 top-50~100 → Cross-Encoder 精排取 top-5~10**。

常见 rerank 模型：bge-reranker、Cohere Rerank、jina-reranker。

## 五、生成阶段：让 LLM 基于检索结果回答

### 5.1 Prompt 构造

把检索到的内容拼进 system prompt，约束模型「基于给定上下文回答」：

```text
你是一个严谨的问答助手。请仅基于以下参考内容回答用户问题。
如果参考内容中没有相关信息，请回答"根据已知信息无法回答"，不要编造。

【参考内容】
[1] 来源：产品手册.pdf / 第3页
    内容：密码重置流程：1. 点击登录页"忘记密码"...

[2] 来源：FAQ.md / 密码相关
    内容：如未收到重置邮件，请检查垃圾邮件箱，或联系...

【用户问题】
忘记密码了怎么办？
```

关键设计：

1. **明确约束**：「仅基于参考内容」「不知道就说不知道」--抑制幻觉
2. **带编号引用**：方便溯源，也便于模型引用具体片段
3. **分隔清晰**：用标记区分参考内容和问题，避免混淆

### 5.2 上下文窗口管理

检索返回的 chunk 不能无限塞进 prompt。要考虑：

- **LLM 上下文窗口**：4K~128K 不等，超出会截断或报错
- **效果衰减**：上下文越长，模型对中间内容的关注度下降（Lost in the Middle 问题）
- **成本**：token 越多，推理越贵

**策略：** 控制参考内容在 2K~4K token 以内，优先放重排序后分数最高的 chunk。如果 chunk 太多，可以做一次**压缩**：让小模型先对每个 chunk 摘要，只保留与问题最相关的句子。

### 5.3 引用溯源

好的 RAG 系统应该让回答**可溯源**：每句话标注信息来自哪个文档的哪个位置。

```
回答：您可以点击登录页的"忘记密码"按钮发起重置 [1]。如果未收到
重置邮件，请检查垃圾邮件箱或联系管理员 [2]。

引用：
[1] 产品手册.pdf - 第3页
[2] FAQ.md - 密码相关
```

实现方式：

- **显式引用**：在 prompt 中要求模型输出 `[n]` 标记
- **后处理**：用 NLP 抽取回答中的句子，匹配回检索片段

## 六、高级 RAG 模式

### 6.1 多轮对话 RAG

多轮对话中，用户的提问可能依赖上下文。比如：

```
用户: React 18 有什么新特性？
助手: ...介绍了 useTransition、Automatic Batching 等
用户: 那个性能的怎么用？  ← "那个性能的"指代不明
```

需要在检索前做**对话改写**：用 LLM 把当前问题结合历史改写成独立可检索的 query。

```
改写前: "那个性能的怎么用？"
改写后: "React 18 useTransition 的使用方法"
```

### 6.2 索引优化

| 技术 | 原理 | 场景 |
|------|------|------|
| 文档摘要索引 | 对每个文档生成摘要，先检索摘要再定位原文 | 长文档 |
| 父子切分 | 检索小 chunk，返回其所属大 chunk | 兼顾检索精度与上下文完整 |
| 层级索引 | 先检索文档级，再检索段落级 | 大规模知识库 |
| 元数据过滤 | 先按时间/分类/标签过滤，再向量检索 | 结构化数据 |

**父子切分** 特别实用：切分时用小 chunk（如 256 token）保证检索精度，但检索命中后返回它所在的父 chunk（如 1024 token）保证上下文完整。

### 6.3 Self-RAG / Corrective RAG

传统 RAG 是「检索了就用」，但检索结果可能不相关。Self-Rag 让模型自己判断：

```
1. 检索到 N 个 chunk
2. 模型判断: 这些 chunk 是否与问题相关？
   ├─ 相关 → 基于内容回答
   └─ 不相关 → 丢弃，直接用模型自身知识回答
3. 回答后判断: 回答是否有依据？
   └─ 无依据 → 标记为"可能不准确"
```

Corrective RAG 更进一步：检索质量低时触发**二次检索**或**网络搜索**补充。

## 七、RAG 工程要点

### 7.1 评估指标

RAG 的评估分三个层面：

| 层面 | 指标 | 含义 |
|------|------|------|
| 检索质量 | Recall@K / Precision@K | 相关文档是否被检索到 |
| 生成质量 | Faithfulness（忠实度） | 回答是否基于检索内容（不幻觉） |
| | Answer Relevance（相关性） | 回答是否切题 |
| 端到端 | Accuracy / 人工评分 | 整体回答是否正确 |

**RAGAS** 是当前最流行的 RAG 评估框架，用 LLM 自动评分。但生产中仍需**人工抽检**兜底。

### 7.2 常见问题与排查

| 问题 | 可能原因 | 解决方向 |
|------|---------|---------|
| 检索不到 | 切分太碎 / embedding 模型差 / query 没改写 | 调 chunk 大小、换模型、加 query 改写 |
| 检索到但不相关 | 没有重排序 / 召回太多噪声 | 加 Cross-Encoder 精排 |
| 回答幻觉 | prompt 约束不够 / 上下文太多 | 加强"仅基于参考内容"约束、控制上下文量 |
| 回答不完整 | chunk 太小、上下文断裂 | 父子切分、增大 overlap |
| 太慢 | 向量库慢 / rerank 候选太多 | 优化 ANN 参数、减少精排候选数 |

### 7.3 技术选型建议

```
知识库 < 10万 chunk:
  向量库: Chroma / FAISS（嵌入式，零运维）
  检索: 纯向量 或 向量+BM25 混合
  rerank: 可选（bge-reranker）

知识库 10万~1000万:
  向量库: Milvus / Qdrant（独立服务，分布式）
  检索: 混合检索（BM25 + 向量）
  rerank: 必须（Cross-Encoder 精排）

知识库 > 1000万:
  向量库: Milvus 集群
  检索: 混合 + 层级索引 + 元数据过滤
  rerank: 必须，可用多级精排
```

## 八、一个最小 RAG 实现

用不到 50 行代码理解 RAG 的核心（Python 伪代码）：

```python
from sentence_transformers import SentenceTransformer
import numpy as np

# 1. 索引
embedder = SentenceTransformer('bge-small-zh')

documents = [
    "密码重置：点击登录页的忘记密码按钮",
    "React 18 引入了 useTransition 用于性能优化",
    "退款流程：在订单页申请退款，3个工作日到账",
    "useTransition 的用法：包裹状态更新即可",
]

# 向量化
doc_embeddings = embedder.encode(documents, normalize_embeddings=True)

# 2. 检索
def retrieve(query, top_k=2):
    query_vec = embedder.encode([query], normalize_embeddings=True)
    # cosine 相似度
    scores = (doc_embeddings @ query_vec[0])
    top_idx = np.argsort(scores)[::-1][:top_k]
    return [documents[i] for i in top_idx]

# 3. 生成
def answer(query):
    contexts = retrieve(query)
    prompt = f"""仅基于以下参考内容回答问题，无相关信息则说不知道。

参考内容：
{chr(10).join(contexts)}

问题：{query}"""
    return llm.chat(prompt)  # 调用 LLM

print(answer("怎么重置密码？"))
# -> 点击登录页的忘记密码按钮即可重置密码。
```

核心就这么简单：**encode → retrieve → prompt**。生产级 RAG 是在这个骨架上叠加切分、混合检索、重排序、评估等工程能力。

## 九、总结

RAG 的本质是把 LLM 从「闭卷考试」变成「开卷考试」。它的完整链路：

```
索引:  文档 → 切分 → embedding → 向量库
检索:  query改写 → 向量+BM25 混合检索 → Cross-Encoder 重排序
生成:  构造带约束的 Prompt → LLM 生成 → 引用溯源
```

**实践中的三条经验：**

1. **切分决定上限**--chunk 策略对效果影响最大，值得花最多时间调
2. **混合检索 + 重排序是标配**--纯向量检索在生产中不够用
3. **评估驱动迭代**--没有评估的 RAG 调参都是「盲调」

RAG 不是银弹，它解决的是「知识注入」问题。当任务需要的是风格适配、领域推理能力提升时，微调更合适。理解两者的边界，才能选对工具。
