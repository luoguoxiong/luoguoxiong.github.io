# RAG 检索增强生成：从原理到工程实践

> 大语言模型知识截止、参数记忆有限、无法访问私有数据。RAG（Retrieval-Augmented Generation）通过「先检索、后生成」的方式，把外部知识注入 LLM，是当前企业落地大模型最务实的方案。本文系统梳理 RAG 的完整流程与工程要点。

## 一、为什么需要 RAG

直接用 LLM 回答问题，会遇到三个硬伤：

1. **知识截止**：模型训练数据有截止日期，无法回答「最新」的信息
2. **幻觉**：模型不知道答案时，会一本正经地编造
3. **私有数据缺失**：企业的文档、数据库、内部知识，模型从未见过

微调（Fine-tuning）能解决一部分问题，但它：

- 成本高（需要标注数据 + GPU 训练）
- 更新慢（每次知识更新都要重新训练）
- 不可解释（不知道答案从哪来）

RAG 的思路很朴素：**既然模型记不住，那就让它「开卷考试」**。每次提问时，先从知识库检索相关内容，再把检索结果和问题一起喂给模型，让模型基于检索到的内容回答。

```
用户提问
   │
   ▼
[检索] 从知识库找相关文档片段
   │
   ▼
[增强] 把检索结果拼进 Prompt
   │
   ▼
[生成] LLM 基于上下文回答
```

### RAG vs 微调

| 维度     | RAG                | 微调               |
| -------- | ------------------ | ------------------ |
| 知识更新 | 增删文档即可，实时 | 需重新训练，慢     |
| 成本     | 低（只推理）       | 高（训练 + 标注）  |
| 可解释性 | 强（可溯源到文档） | 弱                 |
| 适合场景 | 事实问答、知识检索 | 风格学习、领域适配 |
| 幻觉控制 | 好（有据可依）     | 一般               |

两者不是非此即彼：**RAG 管知识，微调管能力**，实践中常组合使用。

## 二、RAG 完整流程

一个生产级 RAG 系统包含三个阶段：**索引、检索、生成**。

```
                         ┌──────────────────────────────────────┐
    离线阶段               │              索引阶段               │
                         │  文档 → 切分 → 向量化 → 存入向量库     │
                         └──────────────┬───────────────────────┘
                                        │
────────────────────────────────────────┼──────────────────────────
    在线阶段                              │
                         ┌──────────────▼───────────────────────┐
    用户提问 ──────────► │              检索阶段                 │
                         │  query 向量化 → 相似检索 → 重排序      │
                         └──────────────┬───────────────────────┘
                                        │
                         ┌──────────────▼───────────────────────┐
                         │              生成阶段                 │
                         │  构造 Prompt → LLM 生成 → 引用溯源    │
                         └──────────────────────────────────────┘
```

下面逐阶段拆解。

## 三、索引阶段：把文档变成可检索的结构

索引阶段决定了检索质量的上限。它包含五步：加载、清洗、切分、向量化、存储。

### 3.1 文档加载

知识库的原始形态多样：PDF、Markdown、HTML、数据库、API。加载时要提取**纯文本 + 元数据**。

```
PDF      -> 提取文字（注意表格、图片、多栏排版）
Markdown -> 去标记，保留标题层级
数据库   -> SQL 查询 + 字段映射
网页     -> 正文抽取（去除导航、广告）
```

**元数据**很重要：来源文件、页码、章节标题、时间戳。它们不仅用于溯源，还能做**过滤检索**（如只搜某个时间段、某个文档分类）。

### 3.2 数据清洗

原始文档加载后，文本里混着大量噪声：HTML 标签、页眉页脚、乱码、重复段落、格式残留。**不清洗直接切分和向量化，垃圾进、垃圾出**，检索质量和生成效果都会大打折扣。

数据清洗是 RAG 最容易被忽视、却对效果影响巨大的环节。一条朴素的经验：

```
数据质量 > 模型能力 > 架构设计
```

再强的 embedding 模型和 rerank，也救不回来一堆噪声文档。

#### 清洗的核心任务

| 任务          | 原因                                    | 处理方式                   |
| ------------- | --------------------------------------- | -------------------------- |
| 去格式残留    | HTML 标签、Markdown 语法符号干扰语义    | 正则去除标签，保留纯文本   |
| 去模板噪声    | 页眉页脚、目录、页码、版权声明          | 按位置/模式识别并移除      |
| 去重复内容    | 多版本文档、转载抄袭导致 chunk 高度重复 | MinHash / SimHash 近似去重 |
| 修编码问题    | 乱码（UTF-8/GBK 混用）、全角半角混排    | 统一编码、半角归一化       |
| 去低质内容    | 空白页、目录页、纯标点段落              | 长度/信息量过滤            |
| 表格/图片处理 | 表格线性化后语义混乱，图片无文字        | 表格转 Markdown、图片 OCR  |
| 敏感信息脱敏  | 身份证、手机号、邮箱等 PII              | 正则匹配 + 替换/掩码       |

#### 清洗流水线示例

```
原始文本
  │
  ├─ 1. 格式清洗：去 HTML 标签、Markdown 符号、控制字符
  ├─ 2. 噪声移除：去页眉页脚、目录、版权声明、多余空行
  ├─ 3. 编码归一化：统一 UTF-8、全角转半角、合并连续空白
  ├─ 4. 质量过滤：丢弃过短段落（<10 字）、纯标点、纯数字
  ├─ 5. 去重：SimHash 相似度去重，保留最优版本
  ├─ 6. 结构恢复：表格转 Markdown、图片 OCR 补充
  └─ 7. 脱敏（可选）：PII 检测与替换
        │
        ▼
      干净文本 -> 进入切分阶段
```

#### 常见清洗问题与排查

| 问题     | 现象                         | 解决                                   |
| -------- | ---------------------------- | -------------------------------------- |
| 表格丢失 | 表格被线性化成一串无意义文字 | 用表格解析库还原结构，转 Markdown 表格 |
| 目录混入 | 检索到目录页而非正文         | 识别目录模式（大量页码 + 标题）并过滤  |
| 重复文档 | 检索结果高度重复，浪费上下文 | SimHash 去重，相似度 > 0.9 只保留一份  |
| 乱码     | embedding 质量骤降           | 统一编码检测（chardet），失败则丢弃    |
| 跨页断裂 | 一个句子被分到两个 chunk     | 先按逻辑段落合并，再切分               |

> **清洗的黄金法则：宁可少不要烂。** 100 篇高质量文档的检索效果，远胜 1000 篇未清洗的文档。脏数据不仅浪费向量库存储，更会污染检索结果，拉低整体质量。

### 3.3 文本切分（Chunking）

切分是 RAG 最影响效果的环节。切太大，检索精度低（一个 chunk 混入太多无关信息）；切太小，语义不完整（上下文断裂）。

**常见策略：**

| 策略       | 原理                               | 适用场景        |
| ---------- | ---------------------------------- | --------------- |
| 固定长度   | 按 N 个 token 切，带 overlap       | 通用、简单      |
| 递归切分   | 按分隔符层级切（段落 > 句子 > 词） | Markdown / 文档 |
| 语义切分   | 用 embedding 相邻度检测主题变化    | 长文档          |
| 结构化切分 | 按 HTML 标签 / Markdown 标题切     | 有结构的文档    |

**Overlap（重叠）** 是固定切分的关键设计：相邻 chunk 保留 10%~20% 的重叠内容，避免一句话被切两半导致语义断裂。

```
chunk1: [A B C D | E F]
chunk2:           [E F | G H I J]
                  ↑ overlap
```

**经验值：** chunk 大小一般取 300~800 token，overlap 取 chunk 的 10%~20%。文档越长越规整，chunk 可以偏大；问答场景 chunk 偏小。

### 3.4 向量化（Embedding）

把文本片段变成高维向量，使语义相近的文本在向量空间距离也近。这是语义检索的基础。

```
"如何重置密码"     -> [0.12, -0.35, 0.88, ...]  (768维)
"密码找回方法"     -> [0.11, -0.33, 0.85, ...]  (向量很近 ✓)
"今天的天气不错"   -> [-0.5, 0.72, 0.01, ...]   (向量很远 ✗)
```

**Embedding 模型选型要点：**

| 类型     | 代表                            | 特点                       |
| -------- | ------------------------------- | -------------------------- |
| 通用英文 | text-embedding-3-small (OpenAI) | 效果好，但需 API、数据出境 |
| 多语言   | bge-m3、multilingual-e5         | 中英文兼顾，可本地部署     |
| 中文优化 | bge-large-zh、m3e-base          | 中文检索效果好             |
| 轻量级   | bge-small、GTE-small            | 速度快、资源省             |

选型核心：**语言匹配 + 维度适中 + 是否可私有部署**。企业内部数据要本地部署 embedding 模型，避免数据外泄。

### 3.5 向量存储

向量库负责存储 embedding 并支持**近似最近邻（ANN）**检索。精确最近邻是 O(N) 的，不可行，所以都用近似算法：

| 向量库   | 索引算法             | 特点                          |
| -------- | -------------------- | ----------------------------- |
| FAISS    | IVF / HNSW           | Meta 开源，纯库，高性能       |
| Milvus   | HNSW / IVF / DiskANN | 分布式、云原生、功能全        |
| Qdrant   | HNSW                 | Rust 实现、轻量、带过滤       |
| Chroma   | HNSW                 | 嵌入式、上手快、适合原型      |
| pgvector | HNSW / IVFFlat       | PostgreSQL 扩展、跟业务库一体 |

**HNSW** 是当前最主流的 ANN 算法：基于分层小世界图，查询速度快、召回率高，但内存占用大。**IVF** 通过聚类分桶加速，内存省但召回略低。

除了向量，还要存**原始文本和元数据**，检索时一并返回用于生成。

## 四、检索阶段：找到最相关的内容

### 4.1 检索方式对比

| 方式            | 原理               | 优势                   | 劣势                 |
| --------------- | ------------------ | ---------------------- | -------------------- |
| 稀疏检索 (BM25) | 关键词精确匹配     | 零依赖、专有名词命中准 | 不理解语义           |
| 稠密检索 (向量) | embedding 语义相似 | 语义泛化（同义、近义） | 精确匹配弱、依赖模型 |
| 混合检索        | 两路并行 + 融合    | 兼顾精确与语义         | 实现复杂             |

**为什么需要混合检索？** 两个典型案例：

```
case 1: 用户搜 "React 18 的 useTransition"
  向量检索: 可能返回 "React Hooks 性能优化"（语义近但没命中）
  BM25: 精确命中 useTransition ✓

case 2: 用户搜 "怎么让组件不卡"
  BM25: "组件""卡" 命中一堆无关文档
  向量检索: 语义匹配 "性能优化""渲染卡顿" ✓
```

### 4.2 混合检索的融合策略

两路检索各取 top-N 后，需要把分数统一排序。常用方法：

**RRF（Reciprocal Rank Fusion）：**

```
score(d) = Σ  1 / (k + rank_i(d))
```

不看原始分数，只看排名。简单、无需归一化，是生产中最常用的融合策略。

**加权融合：**

```
score(d) = w_bm25 × norm_bm25(d) + w_dense × norm_dense(d)
```

需要对两路分数做 min-max 归一化，再按权重加权。权重通过调参确定，一般 0.3~0.7 之间。

### 4.3 查询改写（Query Rewriting）

用户的原始 query 往往口语化、模糊、缺上下文。直接用原 query 检索效果差，需要先改写：

```
原始: "那个性能的"
改写: "React 组件性能优化方案"

原始: "跟上次一样的报错"
改写: （结合历史对话）"TypeError: Cannot read property 'map' of undefined"
```

常见改写技术：

| 技术                | 原理                                            |
| ------------------- | ----------------------------------------------- |
| Query Expansion     | 用 LLM 生成多个同义 query，分别检索后合并       |
| HyDE                | 让 LLM 先「假设一个答案」，用假答案的向量去检索 |
| Query Decomposition | 把复杂问题拆成子问题，分别检索                  |
| Multi-Query         | 生成多个不同角度的 query，扩大召回              |

**HyDE** 的直觉是：答案的 embedding 比问题的 embedding 更接近文档的 embedding（因为答案和文档用词更接近）。

### 4.4 重排序（Reranking）

向量检索是**双塔模型**（query 和 doc 独立编码），速度快但精度有限。重排序用**交叉编码器（Cross-Encoder）**：把 query 和 doc 拼在一起输入模型，输出精确的相关性分数。

```
向量检索 (粗排)                    重排序 (精排)
query embedding ─┐               ┌─ (query, doc1) → Cross-Encoder → 0.92
                  ├─ ANN top-50 ──┤─ (query, doc2) → Cross-Encoder → 0.71
doc embeddings  ──┘               └─ (query, doc50) → Cross-Encoder → 0.05
  (独立编码，快)                     (联合编码，准但慢)
```

Cross-Encoder 不能预计算（query 和 doc 要一起输入），所以只能对少量候选做精排。典型流程：**向量检索取 top-50~100 → Cross-Encoder 精排取 top-5~10**。

常见 rerank 模型：bge-reranker、Cohere Rerank、jina-reranker。

## 五、生成阶段：让 LLM 基于检索结果回答

### 5.1 Prompt 构造

把检索到的内容拼进 system prompt，约束模型「基于给定上下文回答」：

```text
你是一个严谨的问答助手。请仅基于以下参考内容回答用户问题。
如果参考内容中没有相关信息，请回答"根据已知信息无法回答"，不要编造。

【参考内容】
[1] 来源：产品手册.pdf / 第3页
    内容：密码重置流程：1. 点击登录页"忘记密码"...

[2] 来源：FAQ.md / 密码相关
    内容：如未收到重置邮件，请检查垃圾邮件箱，或联系...

【用户问题】
忘记密码了怎么办？
```

关键设计：

1. **明确约束**：「仅基于参考内容」「不知道就说不知道」--抑制幻觉
2. **带编号引用**：方便溯源，也便于模型引用具体片段
3. **分隔清晰**：用标记区分参考内容和问题，避免混淆

### 5.2 上下文窗口管理

检索返回的 chunk 不能无限塞进 prompt。要考虑：

- **LLM 上下文窗口**：4K~128K 不等，超出会截断或报错
- **效果衰减**：上下文越长，模型对中间内容的关注度下降（Lost in the Middle 问题）
- **成本**：token 越多，推理越贵

**策略：** 控制参考内容在 2K~4K token 以内，优先放重排序后分数最高的 chunk。如果 chunk 太多，可以做一次**压缩**：让小模型先对每个 chunk 摘要，只保留与问题最相关的句子。

### 5.3 引用溯源

好的 RAG 系统应该让回答**可溯源**：每句话标注信息来自哪个文档的哪个位置。

```
回答：您可以点击登录页的"忘记密码"按钮发起重置 [1]。如果未收到
重置邮件，请检查垃圾邮件箱或联系管理员 [2]。

引用：
[1] 产品手册.pdf - 第3页
[2] FAQ.md - 密码相关
```

实现方式：

- **显式引用**：在 prompt 中要求模型输出 `[n]` 标记
- **后处理**：用 NLP 抽取回答中的句子，匹配回检索片段

## 六、高级 RAG 模式

### 6.1 多轮对话 RAG

多轮对话中，用户的提问可能依赖上下文。比如：

```
用户: React 18 有什么新特性？
助手: ...介绍了 useTransition、Automatic Batching 等
用户: 那个性能的怎么用？  ← "那个性能的"指代不明
```

需要在检索前做**对话改写**：用 LLM 把当前问题结合历史改写成独立可检索的 query。

```
改写前: "那个性能的怎么用？"
改写后: "React 18 useTransition 的使用方法"
```

### 6.2 索引优化

| 技术         | 原理                                     | 场景                     |
| ------------ | ---------------------------------------- | ------------------------ |
| 文档摘要索引 | 对每个文档生成摘要，先检索摘要再定位原文 | 长文档                   |
| 父子切分     | 检索小 chunk，返回其所属大 chunk         | 兼顾检索精度与上下文完整 |
| 层级索引     | 先检索文档级，再检索段落级               | 大规模知识库             |
| 元数据过滤   | 先按时间/分类/标签过滤，再向量检索       | 结构化数据               |

**父子切分** 特别实用：切分时用小 chunk（如 256 token）保证检索精度，但检索命中后返回它所在的父 chunk（如 1024 token）保证上下文完整。

### 6.3 Self-RAG / Corrective RAG

传统 RAG 是「检索了就用」，但检索结果可能不相关。Self-Rag 让模型自己判断：

```
1. 检索到 N 个 chunk
2. 模型判断: 这些 chunk 是否与问题相关？
   ├─ 相关 → 基于内容回答
   └─ 不相关 → 丢弃，直接用模型自身知识回答
3. 回答后判断: 回答是否有依据？
   └─ 无依据 → 标记为"可能不准确"
```

Corrective RAG 更进一步：检索质量低时触发**二次检索**或**网络搜索**补充。

## 七、RAG 工程要点

### 7.1 RAG 指标体系

RAG 的指标分两大维度：**质量指标**（回答准不准）和**性能指标**（系统快不快）。

#### 7.1.1 质量指标

质量评估贯穿 RAG 的三个环节，每个环节有独立的指标：

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  检索质量    │ ──► │  生成质量    │ ──► │  端到端质量  │
│  召回准不准  │     │  回答好不好  │     │  整体对不对  │
└─────────────┘     └─────────────┘     └─────────────┘
```

**① 检索质量指标**

| 指标        | 公式                               | 含义                               |
| ----------- | ---------------------------------- | ---------------------------------- |
| Recall@K    | 命中相关文档数 / 全部相关文档数    | 该召回的有没有召回（最重要的指标） |
| Precision@K | 命中相关文档数 / 返回的 K 个文档数 | 返回的有多少是相关的               |
| MRR         | 1 / 第一个相关文档的排名           | 相关文档排得有多靠前               |
| NDCG@K      | 位置加权的相关性分数               | 综合排序质量（考虑位置衰减）       |
| Hit Rate    | 有命中 / 无命中（0/1）             | top-K 里有没有相关的               |

重点关注 **Recall@K**：检索阶段是 RAG 的召回层，如果相关文档根本没被检索到，后面生成再强也救不回来。一般看 Recall@5 和 Recall@10。

**② 生成质量指标**

| 指标                              | 含义                           | 判断方式                                 |
| --------------------------------- | ------------------------------ | ---------------------------------------- |
| Faithfulness（忠实度）            | 回答是否基于检索内容，有无幻觉 | 回答中的每个论断能否在参考内容中找到支撑 |
| Answer Relevance（相关性）        | 回答是否切题                   | 回答是否直接回应了用户问题               |
| Context Relevance（上下文相关性） | 检索内容是否与问题相关         | 检索到的 chunk 是不是有用的              |
| Completeness（完整性）            | 是否遗漏关键信息               | 对比标准答案，有无要点缺失               |

**Faithfulness** 是生成质量的核心：它衡量「幻觉率」。一个忠实的 RAG 系统，回答中不应出现检索内容之外的论断。

**③ 端到端指标**

| 指标               | 含义                           |
| ------------------ | ------------------------------ |
| Answer Correctness | 回答与标准答案的语义一致度     |
| Human Rating       | 人工评分（1~5 分），最终金标准 |
| Hallucination Rate | 幻觉回答占比（越低越好）       |

#### 7.1.2 性能指标

生产环境不仅看「准不准」，还要看「快不快」。RAG 的延迟由各环节累加：

```
总延迟 = 索引延迟(离线) + 检索延迟 + 重排延迟 + 生成延迟
                              ↑ 在线关键路径 ↑
```

| 指标                 | 含义                | 典型值   | 关注点               |
| -------------------- | ------------------- | -------- | -------------------- |
| Query Embedding 延迟 | query 向量化耗时    | 10~50ms  | 模型大小、是否 GPU   |
| 向量检索延迟 (ANN)   | 从向量库取 top-N    | 10~100ms | 数据量、索引参数     |
| BM25 检索延迟        | 关键词检索耗时      | 5~50ms   | 倒排索引规模         |
| Rerank 延迟          | Cross-Encoder 精排  | 50~500ms | 候选数量、模型大小   |
| LLM 生成延迟         | 首 token + 完整生成 | 1~10s    | 模型大小、上下文长度 |
| **端到端 P95 延迟**  | 用户提问到回答完成  | 2~15s    | 整体体验             |

**关键性能概念：**

- **TTFT（Time To First Token）**：用户看到第一个字的时间，体感最关键。LLM 流式输出能把 TTFT 从「全部生成完才返回」降到「几百毫秒出首字」。
- **P95 / P99 延迟**：不要只看平均值。用 P95（95% 的请求在这个延迟以下）衡量长尾体验。
- **QPS（吞吐量）**：每秒能处理的请求数。LLM 推理是瓶颈，GPU 并发能力决定 QPS 上限。

**各环节延迟占比（典型值）：**

```
检索+重排    ████░░░░░░  10%~20%
LLM 生成    █████████░  80%~90%  ← 绝对瓶颈
```

优化性能的核心原则：**先优化 LLM 生成**。检索再快，生成慢 10 秒，用户体验也好不了。反过来，生成 2 秒，检索慢 2 秒，体验就差一倍。

### 7.2 生产中如何判断指标

#### 7.2.1 自动化评估：RAGAS

**RAGAS**（RAG Assessment）是当前最流行的评估框架，用 LLM 自动给 RAG 系统打分：

```
评估输入：question, answer, contexts, ground_truth
    │
    ▼
┌────────────┬──────────────┬──────────────┬──────────────┐
│ Faithfulness│ Answer Relev.│ Context Prec.│ Context Recall│
│ 回答有无幻觉│ 回答是否切题  │ 检索是否精准  │ 检索是否全面  │
└────────────┴──────────────┴──────────────┴──────────────┘
```

```python
from ragas import evaluate
from ragas.metrics import (
    faithfulness, answer_relevancy,
    context_precision, context_recall
)

# datasets: 包含 question/answer/contexts/ground_truth
result = evaluate(
    dataset,
    metrics=[faithfulness, answer_relevancy,
             context_precision, context_recall]
)
# 输出每个指标 0~1 分
```

各指标的判断逻辑：

| 指标              | 怎么算的                                        | 高分意味着 |
| ----------------- | ----------------------------------------------- | ---------- |
| Faithfulness      | 拆分回答为论断，逐个检查能否在 context 找到支撑 | 幻觉少     |
| Answer Relevancy  | 用 LLM 从回答反推问题，与原问题比对相似度       | 回答切题   |
| Context Precision | 检索结果中相关 chunk 的排名加权                 | 检索精准   |
| Context Recall    | 相关信息是否都被检索到                          | 检索全面   |

#### 7.2.2 构建评估集

自动评估的前提是有一套**标注数据集**。生产中要构建评估集：

```
字段说明：
  question      用户问题
  ground_truth  标准答案（人工编写）
  contexts      标准相关文档（标注哪些文档应该被检索到）
  answer        RAG 系统实际生成的回答
```

构建方式：

1. **从真实日志采样**：从生产问答日志中抽 100~500 条真实问题
2. **人工标注**：为每个问题标注标准答案和相关文档
3. **覆盖典型场景**：简单事实、多跳推理、模糊问题、边界 case
4. **持续扩充**：上线后定期补充新 case，形成回归测试集

> 评估集不需要大，**100 条高质量标注胜过 10000 条粗标注**。关键是覆盖典型场景和边界 case。

#### 7.2.3 线上监控指标

线上不仅要看质量，还要看性能和用户行为：

| 监控维度 | 指标             | 说明                                    |
| -------- | ---------------- | --------------------------------------- |
| 性能     | P50/P95/P99 延迟 | 分阶段：检索延迟、生成延迟、端到端      |
|          | QPS / 错误率     | 吞吐和可用性                            |
| 质量     | 拒答率           | 模型回答"不知道"的比例（过高 = 召回差） |
|          | 幻觉率           | 抽检或自动评估发现的幻觉占比            |
| 用户行为 | 点赞率 / 复制率  | 用户隐式反馈                            |
|          | 追问率           | 用户是否需要追问（高 = 首次回答不完整） |
|          | 会话时长         | 交互深度                                |

**线上判断原则：**

- **延迟看 P95 不看均值**：平均值掩盖长尾问题
- **质量要抽检**：自动评估 + 人工抽检双保险
- **趋势比绝对值重要**：指标突然下降比绝对数值低更值得关注
- **分场景看**：简单问答 P95 < 3s，复杂推理 P95 < 10s，不同场景标准不同

#### 7.2.4 判断指标好坏的参考线

| 指标             | 及格   | 良好   | 优秀   |
| ---------------- | ------ | ------ | ------ |
| Recall@5         | > 0.70 | > 0.85 | > 0.95 |
| Faithfulness     | > 0.75 | > 0.88 | > 0.95 |
| Answer Relevance | > 0.70 | > 0.85 | > 0.92 |
| 端到端 P95 延迟  | < 10s  | < 5s   | < 3s   |
| 幻觉率           | < 15%  | < 8%   | < 3%   |

> 这些不是绝对标准，具体阈值取决于业务场景。医疗、法律等高风险场景，Faithfulness 要 > 0.95 甚至更高；闲聊场景可以放宽。

### 7.3 常见问题与排查

| 问题           | 可能原因                                   | 解决方向                               |
| -------------- | ------------------------------------------ | -------------------------------------- |
| 检索不到       | 切分太碎 / embedding 模型差 / query 没改写 | 调 chunk 大小、换模型、加 query 改写   |
| 检索到但不相关 | 没有重排序 / 召回太多噪声                  | 加 Cross-Encoder 精排                  |
| 回答幻觉       | prompt 约束不够 / 上下文太多               | 加强"仅基于参考内容"约束、控制上下文量 |
| 回答不完整     | chunk 太小、上下文断裂                     | 父子切分、增大 overlap                 |
| 太慢           | 向量库慢 / rerank 候选太多                 | 优化 ANN 参数、减少精排候选数          |

### 7.4 技术选型建议

```
知识库 < 10万 chunk:
  向量库: Chroma / FAISS（嵌入式，零运维）
  检索: 纯向量 或 向量+BM25 混合
  rerank: 可选（bge-reranker）

知识库 10万~1000万:
  向量库: Milvus / Qdrant（独立服务，分布式）
  检索: 混合检索（BM25 + 向量）
  rerank: 必须（Cross-Encoder 精排）

知识库 > 1000万:
  向量库: Milvus 集群
  检索: 混合 + 层级索引 + 元数据过滤
  rerank: 必须，可用多级精排
```

## 八、一个最小 RAG 实现

用不到 50 行代码理解 RAG 的核心（Python 伪代码）：

```python
from sentence_transformers import SentenceTransformer
import numpy as np

# 1. 索引
embedder = SentenceTransformer('bge-small-zh')

documents = [
    "密码重置：点击登录页的忘记密码按钮",
    "React 18 引入了 useTransition 用于性能优化",
    "退款流程：在订单页申请退款，3个工作日到账",
    "useTransition 的用法：包裹状态更新即可",
]

# 向量化
doc_embeddings = embedder.encode(documents, normalize_embeddings=True)

# 2. 检索
def retrieve(query, top_k=2):
    query_vec = embedder.encode([query], normalize_embeddings=True)
    # cosine 相似度
    scores = (doc_embeddings @ query_vec[0])
    top_idx = np.argsort(scores)[::-1][:top_k]
    return [documents[i] for i in top_idx]

# 3. 生成
def answer(query):
    contexts = retrieve(query)
    prompt = f"""仅基于以下参考内容回答问题，无相关信息则说不知道。

参考内容：
{chr(10).join(contexts)}

问题：{query}"""
    return llm.chat(prompt)  # 调用 LLM

print(answer("怎么重置密码？"))
# -> 点击登录页的忘记密码按钮即可重置密码。
```

核心就这么简单：**encode → retrieve → prompt**。生产级 RAG 是在这个骨架上叠加切分、混合检索、重排序、评估等工程能力。

## 九、总结

RAG 的本质是把 LLM 从「闭卷考试」变成「开卷考试」。它的完整链路：

```
索引:  文档 → 切分 → embedding → 向量库
检索:  query改写 → 向量+BM25 混合检索 → Cross-Encoder 重排序
生成:  构造带约束的 Prompt → LLM 生成 → 引用溯源
```

**实践中的三条经验：**

1. **切分决定上限**--chunk 策略对效果影响最大，值得花最多时间调
2. **混合检索 + 重排序是标配**--纯向量检索在生产中不够用
3. **评估驱动迭代**--没有评估的 RAG 调参都是「盲调」

RAG 不是银弹，它解决的是「知识注入」问题。当任务需要的是风格适配、领域推理能力提升时，微调更合适。理解两者的边界，才能选对工具。
