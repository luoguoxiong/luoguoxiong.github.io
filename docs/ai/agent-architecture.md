# Agent 架构设计有哪些：从单智能体到多智能体编排

> LLM 本身只是「会推理的模型」，Agent 才是「会做事的助手」。本文系统梳理 Agent 的主流架构设计：从最基础的 ReAct 到复杂的多智能体编排，帮助你为不同任务选择合适的架构。

## 一、为什么需要 Agent 架构

大语言模型是无状态的——每次调用都是一次独立推理。它知道很多，但不会：

- **规划**：把一个复杂目标拆解成可执行的步骤
- **行动**：调用外部工具、访问数据、操作系统
- **记忆**：记住上下文和结果，跨步骤推理
- **纠错**：发现自己做错了并改正

**Agent** 就是把这些能力组合起来，让 LLM 围绕一个目标自主运转的「主体」。而**架构**决定了这些能力如何组织：谁在什么时机做什么、信息如何流动、失败如何恢复。

一个 Agent 通常由以下核心模块组成：

```
┌─────────────────────────────────────────────┐
│                  Agent                       │
│  ┌─────────┐  ┌─────────┐  ┌─────────────┐  │
│  │ Planner │  │ Memory  │  │  Tools      │  │
│  │ 规划    │  │ 记忆    │  │  工具/API   │  │
│  └────┬────┘  └─────────┘  └──────┬──────┘  │
│       └──────────┬────────────────┘         │
│                  ▼                          │
│           ┌─────────────┐                   │
│           │  LLM 推理核 │                   │
│           └─────────────┘                   │
└─────────────────────────────────────────────┘
        │ 与外部世界交互（工具、数据、用户）
        ▼
    环境 / 真实世界
```

围绕这些模块如何编排，演化出了不同的架构范式。下面按复杂度从低到高介绍。

## 二、单 Agent 架构

单 Agent 架构由一个智能体独立完成「规划-执行-反思」循环，是最常见也最容易上手的形态。

### 2.1 ReAct 模式（推理 + 行动）

ReAct（Reasoning + Acting）是最经典的单 Agent 架构，由 [Yao et al., 2022](https://arxiv.org/abs/2210.03629) 提出。核心思想是**让推理与行动交替进行**：模型先思考下一步做什么，然后执行动作（调工具），观察结果后再思考，循环直到任务完成。

```
循环：
  思考(Thought)   ->  行动(Action)   ->  观察(Observation)   ->  ...
  我要先查天气     调 weather API      返回：上海今天 28°C
```

```
用户：上海明天适合跑步吗？
Thought: 我需要先查询上海的天气
Action: search_weather(city="上海", date="明天")
Observation: 多云，24~28°C，东南风 3 级
Thought: 温度适宜且无雨，适合跑步
Action: final_answer("适合，多云 24~28°C，体感舒适")
```

**特点：**

| 优点 | 缺点 |
|------|------|
| 实现简单，单循环即可 | 线性思考，复杂任务容易「绕圈」 |
| 可解释性强（思维链可见） | 无全局规划，容易局部最优 |
| 对工具调用天然友好 | 长任务 token 消耗大 |

ReAct 适合**中等复杂度**的任务：问答 + 检索、单工具链调用、数据分析。几乎所有框架（LangChain、agentpack 等）的默认 Agent 都是这个模式。

### 2.2 Plan-and-Execute（计划与执行分离）

与 ReAct 的「边想边做」不同，Plan-and-Execute **先规划、后执行**：先用一个规划器生成完整步骤清单，再逐条执行。这借鉴了人类的做事方式——先定计划再动手。

```
[规划阶段]                          [执行阶段]
目标 -> 生成步骤清单(Plan)  ->   步骤1 -> 执行 -> 验证
                                  步骤2 -> 执行 -> 验证
                                  步骤3 -> 执行 -> 完成
```

例如任务是「整理一份竞品分析报告」：

```
Plan:
1. 确定 5 家主要竞品
2. 搜索各家官网与产品文档
3. 对比功能、价格、定位
4. 生成 Markdown 报告
```

**特点：**

| 优点 | 缺点 |
|------|------|
| 全局规划，避免中途跑偏 | 计划可能过时，需要重规划机制 |
| 每步任务简单，LLM 压力小 | 规划质量依赖 LLM 能力 |
| 可中断、可恢复 | 步骤间上下文传递需要设计 |

Plan-and-Execute 适合**长链路、步骤明确**的任务：周报生成、竞品调研、爬虫分析。注意要配套**动态重规划**（Plan 中某步失败时回到规划器重新调整），否则计划僵化会卡死。

### 2.3 Reflection（反思模式）

Reflection 架构让 Agent **对自己的输出进行自我批判与修正**。核心循环：生成 -> 批评 -> 修正 -> 再生成。

```
初始回答
   │
   ▼
[Critic] 这个回答有什么问题？  ──►  发现遗漏/错误
   │
   ▼
[Revise] 基于批评改进回答
   │
   ▼
再次检查，直到通过质量门槛
```

典型实现（两阶段循环）：

```
# 第一轮：生成初始回答
response = llm.generate(question)

# 反思循环
for _ in range(max_iterations):
    feedback = llm.criticize(response, question)   # 批评
    if feedback.is_good_enough:
        break
    response = llm.revise(response, feedback)      # 修正
```

**特点：**

| 优点 | 缺点 |
|------|------|
| 显著提升输出质量（代码、文案） | 多次调用 LLM，成本翻倍 |
| 减少幻觉和低级错误 | 批评器可能「过度修改」 |
| 实现成本低 | 无外部反馈时提升有限 |

Reflection 适合**质量敏感**的任务：代码生成、论文润色、复杂推理题。可以结合**外部验证**（运行测试、检索事实）组成更可靠的闭环。

### 2.4 Tool-Use Agent（工具调用型）

严格说，工具调用是 Agent 的基础能力而非独立架构，但它的设计方式决定了上层架构。当前主流是 **Function Calling**：把工具用 JSON Schema 描述，LLM 决策是否调用及参数。

```json
{
  "name": "search_web",
  "description": "搜索互联网获取最新信息",
  "parameters": {
    "type": "object",
    "properties": {
      "query": { "type": "string", "description": "搜索关键词" }
    },
    "required": ["query"]
  }
}
```

Agent 执行时返回：

```
assistant: {"tool_calls": [{"name": "search_web", "arguments": {"query": "2026 大模型 Agent 趋势"}}]}
```

**工具设计的原则：**

1. **描述要具体**——描述越清晰，LLM 选择越准
2. **参数要原子化**——一个工具只做一件事
3. **错误要可读**——工具返回的错误应能被 Agent 理解和纠正

## 三、多 Agent 架构

单 Agent 能解决的问题有限：上下文会爆、角色会混淆、复杂任务难并行。多 Agent 架构把任务分给多个「各司其职」的智能体，是当前工程落地的主流方向。

### 3.1 编排者-工作者（Orchestrator-Worker）

一个**编排者** Agent 负责理解任务、拆解子任务并分发给多个**工作者** Agent，最后汇总结果。这是最常见的多 Agent 架构。

```
                     ┌──────────────┐
                     │ Orchestrator │  (编排者：拆解+分发+汇总)
                     └──────┬───────┘
         ┌────────────┬─────┴─────┬─────────────┐
         ▼            ▼           ▼             ▼
    ┌─────────┐ ┌─────────┐ ┌─────────┐  ┌──────────┐
    │ Worker1 │ │ Worker2 │ │ Worker3 │  │ Worker N │
    │ 爬虫    │ │ 分析师  │ │ 写作者  │  │  ...     │
    └─────────┘ └─────────┘ └─────────┘  └──────────┘
```

例如生成一份行业报告：

```
Orchestrator: 拆解任务
  ├─ Worker A（研究员）: 收集行业数据
  ├─ Worker B（分析师）: 分析数据趋势
  ├─ Worker C（写手）: 撰写报告章节
  └─ Orchestrator: 汇总并统一风格
```

**优点**：职责清晰、可并行、每 Agent 上下文小；**缺点**：编排者容易成为瓶颈，通信开销大。

### 3.2 流水线模式（Pipeline）

子任务之间有**严格先后依赖**时，采用管道式：前一个 Agent 的输出是后一个 Agent 的输入。类似工厂流水线。

```
数据采集 -> 数据清洗 -> 特征分析 -> 报告撰写 -> 校对审核
   AgentA      AgentB      AgentC      AgentD      AgentE
```

**特点：**

| 优点 | 缺点 |
|------|------|
| 结构简单，依赖清晰 | 单点故障：一个环节失败全链断 |
| 每 Agent 专注单一职责 | 无法并行，整体延迟累加 |
| 易于测试和替换环节 | 中间产物质量会逐级损耗 |

Pipeline 适合**处理流程固定**的任务：ETL、内容生产流水线、客服工单处理。

### 3.3 辩论模式（Debate / 对抗验证）

多个 Agent **扮演不同立场**对同一问题进行论证或评审，通过相互质疑收敛出更可靠的结论。灵感来自「三个臭皮匠」和 adversarial 思想。

```
             ┌──────────────┐
             │  问题: 方案A │
             └──────┬───────┘
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   ┌────────┐  ┌────────┐  ┌────────┐
   │ 支持方 │  │ 反对方 │  │ 中立评审│
   └───┬────┘  └───┬────┘  └───┬────┘
       └───── 多轮交叉辩论 ─────┘
                  │
                  ▼
             ┌──────────┐
             │ 共识裁决  │
             └──────────┘
```

一个实用变体是 **Generator-Critic**：

- **Generator**：提出方案或代码
- **Critic**：找漏洞、挑毛病
- 循环 N 轮后输出最终版本

**特点**：结论更稳健、能暴露盲点；但 token 成本成倍增加，且辩论可能不收敛。适合**高风险决策**：方案评审、代码审查、安全审计。

### 3.4 分层结构（Hierarchical）

当任务层级很深（团队 > 子团队 > 个人）时，用**多层编排**：高层 Orchestrator 管理中层，中层再管理基层。

```
┌──────────────┐
│  CEO Agent   │  (整体目标拆解)
└──────┬───────┘
       ├─────────────┐
       ▼             ▼
┌──────────┐   ┌──────────┐
│ 产品 Agent│   │ 工程 Agent│   (部门级)
└────┬─────┘   └────┬─────┘
     ▼              ▼
  ┌──────┐     ┌─────────┐
  │ 调研 │     │ 前端/后端│   (个人级)
  └──────┘     └─────────┘
```

分层架构的控制流清晰、天然适配组织模型，但设计复杂、跨层通信延迟高。适合**企业级复杂业务**（如 MetaGPT 的软件公司模拟）。

### 3.5 图结构编排（Graph-based）

把 Agent 建模为**有向图**：节点是 Agent 或动作，边是状态转移。这是当前最灵活的架构，核心是**状态机 + 条件分支**——不同结果走向不同路径。

```
                    失败
        ┌─────────────────────┐
        ▼                     │
   ┌─────────┐   成功   ┌──────────┐   需要工具
   │ 任务理解 │ ──────► │ 规划     │ ─────────► ┌────────┐
   └─────────┘          └──────────┘           │ 调用工具│
                          ▲      │             └───┬────┘
                          │      ▼                 │
                     ┌────────┐  ┌──────────┐      │
                     │ 反思   │◄─ │ 执行     │◄─────┘
                     └────────┘  └──────────┘
```

**LangGraph** 是这个架构的代表实现：显式定义节点与边、支持循环与条件分支、可持久化状态、可人为中断注入人工审核。相比线性 ReAct，图架构把「控制流」从 prompt 中抽离出来变成代码，**更可控、更可测试**。

**特点**：表达力最强、可精确控制；但开发成本高、需要状态管理设计。适合**复杂工作流**：需要人工审批、多条件分支、可恢复重试的真实业务。

### 3.6 黑板模式（Blackboard）

多个 Agent **共享一块黑板（共享内存）**，各自读取、写入、更新，黑板上的「进度」驱动后续 Agent 接力。适合**协作求解同一问题**的场景。

```
┌────────────────────────────────┐
│        黑板 (共享状态)          │
│  ├─ 问题描述                   │
│  ├─ 已收集的数据               │
│  ├─ 各 Agent 的部分结论        │
│  └─ 当前状态: 进行中(60%)      │
└────────────────────────────────┘
     ▲        ▲        ▲
     │        │        │
┌────┴──┐ ┌──┴────┐ ┌─┴─────┐
│ 专家A │ │ 专家B │ │ 专家C │
└───────┘ └───────┘ └───────┘
```

专家 Agent 关注黑板中自己擅长的部分，贡献后黑板状态更新，触发下一轮。适合**多领域知识协同**：故障诊断、复杂规划求解。

### 3.7 群体/协商模式（Swarm）

大量**轻量 Agent 自主行动**，不依赖中央编排，通过协商、投票或经济机制涌现全局行为。OpenAI Swarm 的「Agent 移交（handoff）」就是轻量版：Agent 之间可以互相移交对话控制权。

```
用户 <--> Agent A（前台）
              │ 检测到意图：退款
              ▼ handoff
          Agent B（售后）  ——>  Agent C（财务）  ...
```

**特点**：灵活、无单点瓶颈；但行为不可控、调试困难、可能产生无效循环。适合**客服分流**这类意图明确的场景，不适合需要强保证的业务。

## 四、单 Agent 还是多 Agent？

没有最好的架构，只有最合适的。选型时考虑四个维度：

| 维度 | 单 Agent | 多 Agent |
|------|----------|----------|
| 任务复杂度 | 中低：单链路、检索问答 | 高：多角色、多步骤协作 |
| 成本 | 低（调用次数少） | 高（多个 LLM 轮流调用） |
| 可解释性 | 强（单线程思维链） | 弱（角色间状态分散） |
| 上下文 | 容易超限 | 每 Agent 上下文独立，可控 |
| 并行能力 | 无 | 可并行，吞吐高 |
| 工程复杂度 | 低，一天能跑通 | 高，需设计通信与状态 |

**实践建议：**

1. **先单后多**——大多数任务单 Agent 加好工具就能解决，多 Agent 是「加法」不是「必选」
2. **按角色拆，不按句子拆**——多 Agent 的价值来自角色分工，而不是把 prompt 切开
3. **能 Graph 就别硬套对话**——有明确分支和人工审批时，图结构优于自由对话
4. **给每个 Agent 配工具与记忆**——Agent 的边界 = 工具能力 + 记忆范围

## 五、主流框架一览

| 框架 | 核心架构 | 特点 |
|------|----------|------|
| LangGraph | 图结构 | 状态机驱动、支持循环/分支/人工干预，可落地性强 |
| AutoGen | 对话多 Agent | 多 Agent 群聊、可人类参与，偏研究原型 |
| CrewAI | 编排者-工作者 | 角色/任务/工具抽象，上手快 |
| MetaGPT | 分层+流水线 | 模拟软件公司 SOP，标准流程产物 |
| OpenAI Agent SDK | 移交/单 Agent | 官方 SDK，Agent 间 handoff，简单轻量 |
| agentpack | 单 Agent + 插件 | 生命周期钩子（Extension/Transformer/Tool）扩展，轻量可嵌入 |

选框架的本质是选**架构表达力**：需求是简单问答用 ReAct；需求是确定流程用 Pipeline；需求是复杂分支用 Graph。

## 六、总结

Agent 架构设计没有银弹，但有一条清晰的演进主线：

```
ReAct（边想边做）
   │  任务变长、步骤明确
   ▼
Plan-and-Execute（先计划后执行）
   │  需要多角色、并行
   ▼
多 Agent（编排者/流水线/辩论/图...）
   │  流程复杂、需强控制
   ▼
Graph 状态机（显式控制流 + 人工干预）
```

架构选择的本质，是在**任务复杂度、成本、可控性**三者之间做权衡。给 Agent 设计架构时，记住一句话：**先让单 Agent 跑通，再用架构解决它暴露的问题**——而不是一开始就构建复杂的多智能体系统。
